# Coding Conventions

**Analysis Date:** 2026-11-03

## Naming Patterns

**Files:**
- Python modules are flat `snake_case.py` at the repo root (`helpers.py`, `validation.py`, `ai_generator.py`, `plan_insights.py`).
- Flask blueprints live in `bp/` with one module per route group, named by feature: `bp/auth.py`, `bp/plan.py`, `bp/workout.py`, `bp/history.py`, `bp/constructor.py`, `bp/onboarding.py`, `bp/stats.py`, `bp/profile.py`, `bp/ops.py`, `bp/main.py`.
- Tests are `tests/test_<feature>.py`; end-to-end Playwright tests are `tests/e2e/test_<feature>_e2e.py` or `tests/e2e/test_<feature>.py`.
- Templates are `templates/<name>.html`; static JS is `static/<feature>.js` (e.g. `static/ui.js`, `static/workout_draft.js`).
- Migrations are generated by Alembic under `migrations/` and must not be hand-written (`CLAUDE.md`).

**Functions:**
- `snake_case` everywhere. Module-private helpers are prefixed with a single underscore: `_normalize_plan` (`ai_generator.py`), `_already_saved` and `_parse_sets` (`bp/workout.py`), `_json_error` (`helpers.py`).
- Blueprint view functions are named after the endpoint and referenced as `<bp>.<func>`: `url_for('plan.my_plan')`, `url_for('workout.workout_result', workout_id=...)`.
- Cleaning/validation functions use the `clean_*` prefix and take `(value, low=None, high=None)`-style bounds: `clean_float`, `clean_int`, `clean_exercise_name`, `clean_comment`, `clean_day_title` in `validation.py`.
- Test functions are `test_<behaviour in words>` with underscores, often describing the expected outcome: `test_auto_prefill_applies_suggestion` (`tests/test_workout.py`).

**Variables:**
- `snake_case`. Module-level constants are `UPPER_SNAKE_CASE`: `PLACEHOLDER_EXERCISE`, `DRAFT_CLOCK_SKEW_S`, `RESUBMIT_WINDOW` (`bp/workout.py`), `BODYWEIGHT_EQUIPMENT` (`validation.py`), `MAX_LINES` (`tests/test_module_sizes.py`).
- Time-unit suffixes are used in constant names when relevant (`DRAFT_CLOCK_SKEW_S`).
- Loop/throwaway names are short (`w`, `d`, `e`, `i`) in plan-shaped data builders, as in `tests/conftest.py::make_plan_data`.

**Types and classes:**
- `PascalCase` for SQLAlchemy models in `models.py`: `User`, `WorkoutPlan`, `Workout`, `BodyMetric`, `Exercise`, `ExerciseMedia`, `AnalyticsEvent`, `PersonalRecord`, `WeeklyReport`, `WorkoutTemplate`, `WorkoutSubmission`.
- WTForms classes in `forms.py` are `PascalCase` with a `Form` suffix (login/register forms).
- Type hints are not a project-wide convention. Most modules have no annotations; add them only where they clarify a non-obvious contract.

**Data keys and identifiers:**
- Plan data keys are fixed strings: `week{N}` → `day{M}` → list of `{exercise, sets, reps, weight, comment}` (`WorkoutPlan.data`). Do not rename these keys; the AI flow and manual constructor both write this format.
- Form field names used by the workout page are indexed: `weight_{ex}_{set}`, `reps_{ex}_{set}`, `name_{i}` (`bp/workout.py::_parse_sets`).
- Exercise display names are capitalised via `capitalize_exercise_name` (`validation.py`). Use the Jinja filter `cap_ex` in templates.

## Language and Text

- **Code identifiers and commit messages:** English (`AGENTS.md`, `CLAUDE.md`).
- **User-facing UI text, flash messages, error pages and reports:** Russian. Examples: `flash('Тренировка уже сохранена. Откройте её в истории.', 'info')` in `bp/workout.py`; `_ERROR_PAGES` in `helpers.py`.
- **Code comments and docstrings:** Russian in most modules (e.g. `helpers.py`, `bp/workout.py`, `tests/conftest.py`). New comments may be in Russian to match the surrounding file; keep identifiers in English.
- The product name is never hard-coded. Use `APP_NAME` from `config.py`: `{{ app_name }}` in templates, `current_app.config['APP_NAME']` or `from config import APP_NAME` in Python.

## Code Style

**Formatting:**
- Not enforced by a formatter. `ruff format` must not be run; it creates noisy diffs (`.claude/rules/python.md`).
- Line length is 120 (`ruff.toml`), but E501 is ignored, so long lines are tolerated. Wrap manually to keep lines readable at about 120 columns.
- Quotes: single quotes are dominant in Python code; double quotes appear in some modules. Match the file you are editing.
- Continuation lines are aligned with the opening bracket or hanging-indented, e.g. the `Workout.query.filter(...)` chains in `bp/workout.py`.

**Linting:**
- Tool: ruff (`ruff.toml`). Target `py310`, line length 120.
- Selected rules: `E4`, `E7`, `E9`, `F` (pyflakes + basic pycodestyle errors). `E501` is ignored.
- Run: `.venv/bin/ruff check .` (dev stand) or `ruff check .`. CI runs it in `.gitlab-ci.yml` (stage `test`) and in `.github/workflows/ci.yml`.
- Suppressions use inline `# noqa: <code>` with a reason where needed, most commonly `# noqa: BLE001` for deliberate broad `except Exception` in AI/fallback paths (`ai_generator.py`).
- Auto-fix hook: `.claude/hooks/lint-python.sh` runs `ruff check --fix` after `.py` edits.

**Python version:** 3.10. Do not use syntax or stdlib features newer than 3.10.

## Import Organization

**Order (observed in `bp/workout.py`, `helpers.py`, `bp/plan.py`):**
1. Standard library (`secrets`, `datetime`, `time`, `os`, `re`).
2. Third-party (`flask`, `flask_login`, `sqlalchemy`, `pytest`).
3. Local project modules, usually grouped in the order: stdlib-style modules (`import ai_quota`, `import exercise_catalog as ec`) first, then `from <module> import (...)` lines.

Separate groups with a blank line. Do not add a new tool to enforce import order; ruff `I` rules are not selected.

**Module import style:**
- Use `from helpers import (...)`, `from models import db, Workout`, `from validation import clean_int` for named symbols.
- Use `import exercise_catalog as ec`, `import report as report_mod`, `import ai_quota` when the module is used as a namespace.
- Tests that stub AI behaviour must import the **consuming** module and patch its name (see Mocking in `TESTING.md`).

**Path Aliases:**
- None. All imports are absolute relative to the repo root (flat layout), plus `bp.<name>` for blueprints.

**Circular import rule:**
- Blueprints must **not** import from `app`. Shared objects go in `extensions.py`; shared helpers in `helpers.py`.
- `tasks.py` imports `app` and `bp.plan` lazily inside task functions. Task functions must stay top-level.

## Error Handling

**Web/HTML routes:**
- Use `abort(<code>)` for HTTP errors (`bp/workout.py` imports `abort`). Error pages render the single `templates/error.html` for 400/403/404/405/413/500, with the Russian copy from `_ERROR_PAGES` in `helpers.py`.
- Flash user-visible feedback with `flash(message, category)` and redirect, e.g. `redirect(url_for('workout.workout_today'))`.
- Return `303` (redirect after POST) for successful form submissions; the test `tests/test_workout.py` asserts `status_code == 303`.

**JSON / `/api/*` routes:**
- Errors return JSON, never HTML. Use the helper `_json_error(message, code)` from `helpers.py`, which returns `{'status': 'error', 'message': ...}` and the status code.
- Fetch-driven forms send the header `X-Requested-With: fetch` (constants `FETCH_HEADER` / `FETCH_HEADER_VALUE` in `helpers.py`). Check it with `wants_json()` to decide between a JSON response and a redirect.
- CSRF failures on `/api/*` return JSON 400; on HTML routes they flash and redirect to the form (`AGENTS.md`).

**Validation:**
- Validate and clean all external input through `validation.py` (`clean_int`, `clean_float`, `clean_comment`, `validate_profile`). Return `None` for missing/invalid values rather than raising, and treat `0` kg as "weight not entered" (`_parse_sets` in `bp/workout.py`).
- Profile enum options and ranges live in `validation_options.py` and are re-exported from `validation.py`. Add new options there first.

**AI / external calls:**
- Gemini failures are caught broadly with `except Exception:  # noqa: BLE001` and converted into fallbacks (`ai_generator.py`). Keep this pattern limited to the AI boundary; do not spread broad excepts into normal code.
- Missing API key raises `RuntimeError` (`ai_generator.py`, `GOOGLE_API_KEY не задан`).
- Plan output is never trusted as-is: it passes through `_normalize_plan` / `ensure_focus_exercises` (`ai_generator.py`, `ai_normalize.py`).

**Database:**
- Handle integrity races explicitly: `from sqlalchemy.exc import IntegrityError` in `bp/plan.py`.
- After mutating a JSON column, call `flag_modified(obj, 'data')` (`sqlalchemy.orm.attributes`) before `db.session.commit()`, as done in `bp/workout.py` and `tests/test_workout.py`.

## Logging

**Framework:** Flask/Python `logging` through `current_app.logger` (no `print` in application code).

**Patterns:**
- Use `%s` placeholders, not f-strings, in logger calls: `current_app.logger.info('Вход: %s', email)` (`bp/auth.py`).
- Levels: `info` for normal business events (login, registration, password reset), `warning` for failed attempts (`Неудачный вход`).
- Analytics events are recorded through `log_event` (helpers) into `AnalyticsEvent`, not through the logger.
- Test runs set `LOG_LEVEL=WARNING` (`tests/conftest.py`).

## Comments

**When to comment:**
- Explain *why* a non-obvious rule exists, especially data-shape decisions and business invariants. Examples: why `weight=0` becomes `None` (`bp/workout.py::_parse_sets`), why re-submits within 15 minutes redirect to the saved workout (`RESUBMIT_WINDOW`).
- Reference the audit/ticket id when a rule came from one (e.g. `# E-02:` in `tests/test_module_sizes.py`, `# G-04:` in `.coveragerc`). Do not invent new IDs.
- Do not narrate what the next line does.

**JSDoc/TSDoc:** Not applicable (no TypeScript). Python docstrings are used at module level and for helpers with non-obvious behaviour; they are written in Russian and are short (one or two lines).

## Function Design

**Size:** No hard limit enforced except the module size guard. `tests/test_module_sizes.py` fails if any module in the repo root or `bp/` exceeds 600 lines. When a module approaches the limit, split it (the AI layer was split into `ai_safety`, `ai_prompts`, `ai_normalize`, `ai_analysis`, `ai_plan_gen`).

**Parameters:**
- Pass `user_id` (an int) into helpers rather than the `current_user` object when the function can be reused outside a request.
- Keyword arguments for optional flags (`allow_custom=False`, `extra_max`).

**Return Values:**
- Pure helpers return plain dicts/lists/strings (`report.py` is a set of pure functions).
- Route functions return `render_template(...)`, `redirect(...)`, or `jsonify(...)`/a `(dict, status)` tuple for JSON.

## Module Design

**Exports:**
- Facade modules re-export their internals so that existing imports and patch targets keep working. Examples: `ai_generator.py` re-exports `ai_safety`, `ai_prompts`, `ai_normalize`, `ai_analysis`, `ai_plan_gen`; `validation.py` re-exports `validation_options`; `bp/plan.py` re-exports `plan_insights`. When moving a function, keep it importable from the facade.
- `ai_analysis` and `ai_plan_gen` call `_generate`, `_extract_json`, `_normalize_plan` through `ai_generator` at call time, so patches on `ai_generator.<name>` still take effect. Preserve this call-time lookup.

**Barrel Files:** No `__init__.py` barrels. `bp/` is imported module by module (`import bp.history as history_bp`).

**Blueprints:**
- Each blueprint is `bp = Blueprint('<name>', __name__)` at module top. Registration happens in `app.py` with no URL prefix, so endpoint names are `<bp>.<func>`.
- When an endpoint is renamed or moved, update the active-nav list in `templates/base.html` (it selects the item by `request.endpoint`).

## Frontend Conventions (templates and static)

- Templates extend `templates/base.html` and fill the blocks `title`, `body_class`, `body`, `scripts`.
- No inline `<style>` blocks and no inline JS handlers such as `onclick`. Use `data-*` attributes and delegated listeners in `static/ui.js`.
- Styling uses CSS variables from `static/style.css` (`--bg`, `--card`, `--text`, `--accent`, `--muted`). Dark theme is `[data-theme="dark"]`, stored in `User.theme`.
- Chart.js is vendored at `static/vendor/chart.umd.min.js`. Do not add a CDN link.
- JS requests must send the CSRF token via the helper in `static/ui.js`.

Example of the expected pattern:

```html
{% extends "base.html" %}
{% block title %}Тренировка · {{ app_name }}{% endblock %}
{% block body %}
  <button type="button" class="btn" data-action="save-draft">Сохранить</button>
{% endblock %}
```

```javascript
// static/ui.js style: delegate on document, read data-* attributes
document.addEventListener('click', (e) => {
  const el = e.target.closest('[data-action="save-draft"]');
  if (!el) return;
  // ...
});
```

## Adding New Code: Checklist

1. Profile option or limit: add to `validation_options.py` first, then expose through `validation.py`.
2. Route: add to the matching `bp/*.py` blueprint; do not import from `app`. Use the `new-route` skill (`.claude/skills/new-route`) for the full checklist.
3. Model change: edit `models.py`, then `flask --app app db migrate -m "..."`. Never hand-write a migration.
4. Template: extend `base.html`, use `{{ app_name }}`, `data-*` for behaviour, no inline style/JS.
5. Run `.venv/bin/ruff check .` and `.venv/bin/python -m pytest -q` before committing.
